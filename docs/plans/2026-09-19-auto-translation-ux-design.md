# 自动翻译：自动化面全景设计 + 开关交互设计

配套文档：[2026-09-19-auto-translation-design.md](./2026-09-19-auto-translation-design.md)（现状盘点与差距分析）。
那份说"缺什么"，这份说"做成什么样"。

两部分：
- **第一部分**：整体能自动化的地方 —— 五个自动化面，共用一套规则。
- **第二部分**：启用/关闭的交互 —— 四个触点，一个状态机，用户只需要学会一件事。

# 第一部分 · 能自动化的地方

## 1.0 唯一的前提：五个面共用一套规则

```
shared/site-rules.js                    ← 唯一真相源，纯函数，可单测
  storage.sync.siteRules = { "x.com": "always", "mybank.com": "never" }
  storage.sync.autoTranslate = true                  // 全局闸门
  decide({ host, path, pageLang, targetLang, settings }) → 'auto' | 'ask' | 'off'
```

五个面（正文 / 字幕 / 输入框 / 文件 / 图像）**全部读这一个 store**，不各自建表。

理由不是洁癖，是可解释性：用户在 youtube.com 上关掉了自动翻译，字幕却还在自动翻 ——
这种状态用户无法理解，也无法自行修复，而且一定会发生（因为字幕现在就有一个独立开关）。
**一个域名，一个答案。**

规则粒度 = **域名**。路径级差异（arXiv 的 `/pdf/` 除外、GitHub 的 diff 视图除外）只存在于
**内置规则表**里，用户不可配。用户能配的维度越少，这个功能越好用。

## 1.1 五个自动化面

| 面 | 「自动」的含义 | 触发器 | 成本 | 阶段 |
| --- | --- | --- | --- | --- |
| **S1 页面正文** | 打开即译、滚动续译、换路由重译 | 规则 + 页面语言判定 + MutationObserver/IntersectionObserver | 每页一次引擎调用 | P0 |
| **S2 视频字幕** | 打开视频即有双语字幕；必要时自动打开 CC | `provider.canActivate()` + 同一套规则 | 逐句，量小 | P2 |
| **S3 输入框** | 打字时识别语言，就地提示"译成英文？" | 输入事件 + 语言判定 | 极小 | P3 |
| **S4 文件** | 拖入即译（srt/vtt/ass/txt/md） | 文件类型 | 一次性 | P4 |
| **S5 图像 / 漫画** | 自动**出现入口**，绝不自动开跑 | 规则 + 页面形态探测 | 付费额度 | 受限 |

S5 的限制是硬性的：漫画和 PDF 走账号付费额度，**自动触发 = 自动扣用户的钱**。
自动化在这一面只能做到"入口自己出现在正确的地方"，不能做到"任务自己开始"。

## 1.3 S2 视频字幕 —— 站点全景

| 站点 | 字幕来源 | 现状 | 自动化成本 |
| --- | --- | --- | --- |
| YouTube | `/api/timedtext`（MAIN world 拦截） | provider 已有，需观众先开 CC | **低**：加 `enableNativeCaptions()` 点一下 `.ytp-subtitles-button` |
| Coursera / Udemy / edX / TED / Vimeo / Khan | 标准 `<track>` / TextTrack | `TextTrackProvider` 已能接 | **接近零**：只差允许把 `disabled` 轨提到 `hidden` |
| Bilibili | 站内字幕 JSON | 无 | 中：一个 provider |
| Netflix / Prime / Disney+ / HBO | 播放器自管，不落 TextTrack | 无 | 高：每站一个 MAIN-world 网络观察 provider，且需评估条款合规 |
| **Zoom / Meet / Teams 实时字幕** | 字幕是 DOM 文本流 | 无 | 中，但这是**第三种 provider 形态（DOM provider）**：做一个模板出来，所有"字幕画在 DOM 里"的站点通吃 |
| 播客 transcript（Spotify / Apple） | DOM 文本 | 无 | 与上同形 |

**结论**：`TextTrackProvider` 已经覆盖了一大片教育类站点，卡点只有一个 ——
「我们从不替观众打开字幕」这条现行铁律。改掉它（加开关、改 CLAUDE.md），
YouTube + 教育站一次到位，这是投入产出比最高的一格。

## 1.4 S3 输入框

场景：在英文站的输入框里打中文、在中文站的搜索框里打英文。
自动化 = 检测到输入语言 ≠ 页面语言时，输入框右下角出现一个极小的「译成 EN」芯片，点了才译。
**永不自动改写用户输入**（那是灾难）。成本极低，风险极低，但价值中等，排 P3。

## 1.5 S4 文件

| 形态 | 现状 | 判断 |
| --- | --- | --- |
| **字幕文件 srt / vtt / ass** | 无 | **性价比最高的空白**：`shared/caption-core.js` 已经会解析 VTT/json3/srv3，翻译链路现成，只差一个上传页 + 双语导出 |
| EPUB / Mobi | 扩展侧无（saas 侧有阅读台） | 与 saas 打通，不在扩展里重做 |
| 本地 txt / md | 无 | 低优先 |
| 本地 PDF | 已有（右键 → 翻译本地 PDF） | 已覆盖，付费，不自动 |

## 1.6 S5 付费面的自动化边界（硬约束）

```
  可以自动：入口出现   ← 规则说"这是漫画站"→ 悬浮球长出「翻译这页漫画」
  绝不自动：任务开始   ← 扣额度的动作永远需要一次点击
```

arXiv `/pdf/` 同理：识别到了，给一条提示条「翻译这篇论文（约 N 页额度）」，**点了才跑**。
这条不是保守，是底线：自动扣费一次就会丢掉用户。

# 第二部分 · 启用 / 关闭的交互设计

## 2.0 四条设计原则

1. **状态，不是动作。** "翻译这个网站"是一个开关，不是一次操作。用户不该被迫在
   「翻译此页一次」和「总是翻译此站」两个并列菜单项之间做分类 —— 那是把实现模型泄露给用户。
2. **决定发生在最有上下文的时刻。** 用户刚亲手翻完一页时，最清楚"我想不想每次都这样"。
   设置页永远给不了这个时刻。
3. **撤销比设置重要。** 开错了能立刻在原地关掉，比"能在设置页精细配置"重要一个数量级。
4. **成功 = 没有交互。** 自动翻译跑得好的时候，不应该弹任何东西。toast 是对成功的惩罚。

## 2.1 四个触点（全部交互只有这四处）

### 触点 1 · 自动翻译发生时 —— 不弹东西

页面加载 → 判定 → 静默翻译。唯一可见痕迹是悬浮球本身：

```
   ( ⇄ )      普通态：本站不自动翻
   ( ⇄ )˙     右上角一个小点：本站已设为自动翻译
   ( ◠ )      翻译中：一圈细进度环，2 秒内消失
```

没有横幅、没有 toast、没有"已为您自动翻译"。悬浮球已经在那儿了，它就是状态指示器。

### 触点 2 · 启用 —— 一次追问，只问一次

用户在一个还没规则的站（`ask` 态）手动翻了一次整页。**翻译完成后**，悬浮球旁浮出一条单行条，
5 秒无操作自动消失：

```
   ┌───────────────────────────────────────┐
   │  以后自动翻译 x.com？   总是    不用   │
   └───────────────────────────────────────┘
                                      ( ⇄ )
```

| 点击 | 结果 |
| --- | --- |
| 总是 | `siteRules["x.com"] = "always"`，下次打开即译，小点亮起 |
| 不用 | `= "never"`，以后不再问、不再自动翻 |
| 不理它 | 保持 `ask`；下次在该站翻完再问一次，**累计 3 次不回应后永久静默** |

这是唯一的启用路径。用户不需要知道"站点规则"这个概念的存在，也永远不需要为了打开它去找设置页。

### 触点 3 · 关闭 —— 分清用户想的两件事

用户说"关掉"时，其实是两件不同的事，必须用两个不同的动作对应：

| 用户心里想的 | 动作 | 效果 |
| --- | --- | --- |
| **"这一页我想看原文"** | 点悬浮球 | 还原原文（一次性，**不改规则**）。再点一次，再译回来 |
| **"这个站以后别自动翻了"** | 悬浮球菜单第一项「不再自动翻译 x.com」<br>（仅在该站为 `always` 时出现） | `= "never"`，立即还原原文 |

第二项之所以放在菜单**第一位**且**仅在需要时出现**，是因为它是自动化功能里唯一高频的"后悔"操作。
让用户为了关掉一个站去设置页翻列表，是这类功能差评的第一来源。

### 触点 4 · 全局闸门 —— popup 一行

```
   ┌─────────────────────────────────┐
   │  ⚡  自动翻译             [ 开 ] │
   │  ⇄   翻译此页                   │
   │  ●   悬浮球              [ 开 ] │
   │  ▭   视频字幕            [ 开 ] │
   └─────────────────────────────────┘
```

复用 popup 现有的 `kbd` 状态芯片形态（`floatBallStatus` / `youtubeCaptionsStatus` 已经是这个样子，
见 `popup/popup.html:34`、`:43`）。关掉 = 所有 `always` 规则**暂停但不丢失**，再开即恢复。

这是"今天别烦我"的总闸，必须在一个固定、好找的位置 —— popup 是唯一合适的地方。

## 2.2 状态机：一个域名只有三态

```
                 翻完后追问 →「总是」
        ask ──────────────────────────→ always
         │                                 │
         │ 追问 →「不用」      菜单「不再自动翻译此站」
         ↓                                 ↓
        never ←────────────────────────────┘
```

- `ask`（默认）：不自动翻，但手动翻完后追问（≤3 次）。
- `always`：打开即翻、滚动续翻、换路由重翻。
- `never`：不自动翻，也不再追问。手动翻译**依然可用**（`never` 关的是自动，不是功能）。

三态之外不设第四态。特别是不做"仅本次会话""仅此路径"这类精细态 —— 它们会让状态指示器无法用一个小点表达。

## 2.3 快捷键：只做一个

`Alt+A` = 与悬浮球单击**完全同义**（翻译 / 还原）。

对手有两个（Alt+A 翻译、Alt+W 强制翻全页）。我们不做第二个：
"翻不全"应该用内置规则修，不该让用户用第二个快捷键绕过。
一个功能需要用户记两个快捷键，通常说明第一个没做好。

## 2.4 设置页 = 审计，不是配置

设置页的自动翻译区只放两样东西：

1. **已保存的站点表** —— 域名 + 状态 + 一个 ✕，用于清理误操作。**只读为主，不用于添加。**
2. **高级项（默认折叠）** —— 自动模式引擎（默认 builtin）、自动翻译的语言范围、AI 引擎每日字符预算。

设计目标：**一个普通用户从装上到用熟，一次都不需要打开这一页。**

## 2.5 顺带收敛：让开关变少而不是变多

现在用户面对的翻译类开关：悬浮球开关、YouTube 字幕开关（默认关）、未来的自动翻译开关。
上线后应收敛为 **1 个主开关 + 1 个副作用开关**：

| 开关 | 去向 |
| --- | --- |
| 「自动翻译」（新，全局） | **主开关**。开 ⇒ 正文、字幕、输入框提示全部按站点规则自动 |
| `enableYoutubeCaptionTranslation`（现有，默认关） | **并入主开关**。站点规则对视频站同样生效：youtube.com 设 `never` ⇒ 字幕也不翻 |
| `autoEnableCaptions`（新） | **唯一保留的独立开关**，默认关。因为它有副作用（自动打开播放器的 CC，改动了页面状态），必须单独同意 |
| 悬浮球显示/隐藏 | 不变，与翻译无关 |

## 2.6 默认值（决定了这个功能的第一印象）

| 项 | 默认 | 理由 |
| --- | --- | --- |
| `autoTranslate` 全局 | **开** | 关着的自动化等于不存在。真正的保护是下面三条，不是默认关 |
| 站点默认态 | `ask` | 不主动翻任何站；所有 `always` 都是用户亲手点出来的 |
| 自动模式引擎 | `builtin` | Chrome 内置 Translator：本地、免费、无额度。这是"默认开"能成立的前提 |
| AI 引擎用于自动模式 | **关**，需二次确认 + 每日预算 | 这是唯一会花钱的路径 |
| `autoEnableCaptions` | **关** | 有副作用 |
| 内置 `never` 黑名单 | 网银 / 支付 / localhost / 内网 / 密码管理器 | 上架合规：自动翻译意味着页面内容在用户没点任何按钮的情况下被发往第三方 |

## 2.7 明确不做的东西（防止交互膨胀）

- ❌ 「翻译此页一次」与「总是翻译此站」两个并列菜单项 —— 对手最劝退的一步。
- ❌ 首次安装的多步引导向导。
- ❌ 每站的独立配置面板（选择器、延迟、引擎）—— 这些进内置规则，用户看不见。
- ❌ 「自动翻译语言列表」的默认可见入口 —— 99% 的用户只有一个目标语言，放进高级折叠区。
- ❌ 第四种站点状态、第二个快捷键、第二个进度指示器。

## 2.8 交付顺序（交互部分）

| 批 | 内容 | 用户可感知的变化 |
| --- | --- | --- |
| 1 | 状态机 + `shared/site-rules.js` + 触点 2（追问条）+ 触点 3（菜单项） | 翻完一次能记住这个站 |
| 2 | 触点 1（悬浮球状态点 / 进度环）+ 触点 4（popup 主开关） | 能看出来它在工作、能一键停 |
| 3 | 设置页审计表 + 高级折叠区 + `Alt+A` | 能清理、能调 |
| 4 | 开关收敛（字幕并入主开关 + `autoEnableCaptions`） | 开关变少 |

## 2.9 已裁决

> 2026-09-19 更新：第三方评审 §6.3 独立给出同一结论（单击翻译/恢复 + 小箭头开菜单），
> 两侧收敛，**定案为"改"**。见 [核验与综合](./2026-09-19-parity-review-synthesis.md) §5。
> 评审还建议保留"沿用原点击菜单模式"作为可选项 —— **不采纳**：一个动作两种语义，
> 说明文档和快捷键都要分叉，与"交互越简单越好"相悖。

**悬浮球单击的语义**。现在单击 = 打开菜单（`content/content-float-ball.js:324`），
所以"翻译整页"要两次点击。本设计把单击改为「翻译 / 还原」切换，菜单移到
hover 展开的 `···`（触屏为长按）。

- 改：与 `Alt+A`、与"点一下关掉"完全一致，最省事。
- 不改：保留肌肉记忆，但"关掉译文"永远是两次点击，触点 3 的体验打折。

定案：改。理由：自动翻译上线后，用户在悬浮球上最高频的动作会从"翻译"变成"还原 / 重翻"，
而菜单里的项（输入框翻译、划词、漫画、设置）都是低频项。

| 议题 | 评审主张 | 本文主张 | 定案 |

| popup 信息架构 | 9 行控制面板（§6.2） | 一行开关 | **四行**：当前站点＋引擎状态 / 翻译·恢复 / 本站自动翻译 / 暂停本页 |
| 首次使用 | 四步引导（§6.1） | 明确不做引导向导 | **不做向导**；只取"语言包准备可见"一项，做成首次翻译时的非阻塞状态条 |
